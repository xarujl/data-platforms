# ДЗ2 — YARN и MapReduce

## Схема

| Узел из inventory ДЗ1 | Добавляемые сервисы |
| --- | --- |
| edge | Ansible и SSH-туннели |
| nn (`namenode`) | ResourceManager, NodeManager, JobHistoryServer |
| nn, dn0, dn1 (`datanodes`) | По одному NodeManager |

После этапа ДЗ1 на трёх узлах должны быть установлены Hadoop 3.4.0 и Java 11, а HDFS — запущен с тремя живыми DataNode и выключенным safe mode. Пользователь демонов — `hdfs`, группа — `hadoop`, каталог Hadoop — `/opt/hadoop-3.4.0`. По умолчанию запуск сначала выполняет ДЗ1, включая установку Ansible на edge. При `--skip-hw1` HDFS и Ansible должны быть готовы заранее. Перед настройкой плейбук проверяет состав inventory, согласованность лимитов контейнеров и текущее состояние HDFS.

## Inventory и настройки

Используются существующие локальные файлы ДЗ1:

- `hw1/infra/control-inventory.ini` — внешний адрес edge и SSH-пользователь;
- `hw1/infra/edge/inventory.ini` — внутренние адреса, группы и SSH-ключ на edge;
- `hw1/infra/edge/group_vars/all.yml` — версия, пути и окружение Hadoop.

Новые inventory для ДЗ2 создавать не нужно. При запуске непосредственно с edge нужен только внутренний `hw1/infra/edge/inventory.ini`; внешний inventory не используется. Если файлов ещё нет, скопируйте примеры из ДЗ1 и заполните адреса. Внешний inventory должен содержать узел `edge-node` в группе `edge`. Внутренний ключ должен существовать **на edge** по пути из `ansible_ssh_private_key_file`; скрипт не переносит приватные ключи.

Настройки YARN находятся в `edge/group_vars/all.yml`. Адрес ResourceManager и JobHistoryServer берётся из первого узла группы `namenode`, адреса NodeManager — из группы `datanodes`.

## Запуск с внешнего устройства

На локальном устройстве нужны Ansible, Python 3 и SSH. Доступ по SSH и `sudo` на VM должен быть настроен, как для ДЗ1.

Из корня репозитория в ветке `hw2`:

```bash
cd hw2/infra
./deploy.sh
```

Скрипт сначала выполнит `hw1/infra/deploy.sh`, затем скопирует плейбуки ДЗ1 и ДЗ2, внутренний inventory и общие переменные ДЗ1 в `/home/team/yarn-ansible`, затем выполнит внутренний деплой с edge. Путь меняется через `yarn_edge_project_dir`. Сам этап ДЗ2 пакеты не устанавливает. Для запуска только ДЗ2 используйте `./deploy.sh --skip-hw1`.

## Запуск с edge

Клонируйте ветку `hw2` на edge и заполните внутренний inventory:

```bash
git clone -b hw2 https://github.com/xarujl/data-platforms.git
cd data-platforms
cp hw1/infra/edge/inventory.ini.example hw1/infra/edge/inventory.ini
# Заполните внутренние IP и путь к существующему SSH-ключу на edge.
```

Из корня репозитория:

```bash
cd hw2/infra/edge
./deploy.sh
```

После копирования с локального устройства:

```bash
cd /home/team/yarn-ansible/hw2/infra/edge
./deploy.sh
```

В обоих вариантах `deploy.sh` сначала выполняет ДЗ1, затем ДЗ2. Существующий NameNode повторно не форматируется. Если ДЗ1 завершается с ошибкой, ДЗ2 не запускается. На edge Ansible при необходимости устанавливается скриптом ДЗ1. Для повторной настройки только YARN используйте `./deploy.sh --skip-hw1`.

## Что выполняется

`edge/site.yml` последовательно запускает:

1. `prepare.yml` — исправляет привязку имени VM к loopback в `/etc/hosts`, проверяет HDFS, создаёт локальные каталоги YARN и каталоги истории в HDFS, записывает `yarn-site.xml`, `mapred-site.xml` и heap-настройки демонов.
2. `yarn.yml` — запускает ResourceManager, три NodeManager и JobHistoryServer, ждёт доступности портов ResourceManager и JobHistoryServer с edge. Готовность NodeManager проверяется через HTTP в `check.yml`.
3. `check.yml` — проверяет здоровье NodeManager через HTTP, регистрацию трёх узлов, запускает WordCount, сверяет результат и проверяет завершение в ResourceManager и JobHistoryServer.

WordCount использует уникальные локальный и HDFS-каталоги, удаляемые после проверки. На выполнение задания отводится 300 секунд; лимит меняется через `yarn_smoke_timeout_seconds`. При ошибке или таймауте скрипт пытается остановить найденное тестовое приложение. История задания остаётся в JobHistoryServer.

HDFS не форматируется, его конфигурация и демоны не меняются. При изменении `yarn-site.xml` или блока heap в `yarn-env.sh` перезапускаются ResourceManager и NodeManager; при изменении `mapred-site.xml` или блока heap в `mapred-env.sh` — JobHistoryServer. Исправление `/etc/hosts` также вызывает перезапуск этих демонов на затронутом узле, чтобы они заново разрешили имена. Повторный запуск без изменений конфигурации не перезапускает демоны, но всегда выполняет новую тестовую задачу. Изменения настроек применяйте без активных заданий: перезапуск демонов может их прервать.

Как и в ручном гайде, используются `--daemon start/stop`, без systemd и автозапуска после перезагрузки. После перезагрузки повторите `deploy.sh` без `--skip-hw1`: он последовательно восстановит HDFS и YARN.

## Исправление привязки имени к loopback

На текущих VM имя узла одновременно записано в `/etc/hosts` с внутренним IP и с `127.0.1.1`. Из-за повторного разрешения имени ResourceManager и JobHistoryServer могут слушать loopback даже при указании внутреннего IP в XML.

Перед запуском сервисов плейбук получает короткое имя каждой VM и заменяет адрес в строке `127.0.1.1`, содержащей только это имя и его FQDN-варианты, на `ansible_host` из inventory ДЗ1. Имена, комментарии и остальные записи сохраняются; `127.0.0.1 localhost` не меняется. Например:

```text
# До
127.0.1.1 team-35-nn.hse.c.mws team-35-nn
# После
10.35.0.11 team-35-nn.hse.c.mws team-35-nn
```

Перед изменением создаётся резервная копия `/etc/hosts`. Чтобы применить исправление после неудачного запуска, повторите `hw2/infra/deploy.sh` с локального устройства: он доставит обновлённые плейбуки на edge и перезапустит затронутые демоны YARN/MapReduce.

## Лимиты для текущих VM

К ручному гайду добавлены явные лимиты для VM с 2 CPU и примерно 4 GiB RAM:

| Параметр | Значение |
| --- | --- |
| Память контейнеров на nn | 1024 MiB |
| Память контейнеров на dn0 и dn1 | По 2048 MiB |
| vcores на каждом NodeManager | 2 |
| Минимальный / максимальный контейнер планировщика | 512 / 2048 MiB |
| Контейнер AM, map, reduce / Java heap | 512 / 384 MiB |
| Heap ResourceManager / NodeManager / JobHistoryServer | 512 / 256 / 256 MiB |

На nn оставлено больше памяти для NameNode и остальных демонов. Проверка физической памяти контейнеров включена; проверка виртуальной памяти отключена, чтобы резервирование адресного пространства JVM не приводило к остановке небольших контейнеров. Если меняются ресурсы VM или нагрузка, пересмотрите лимиты в `edge/group_vars/all.yml`.

Сбор фактических RAM/CPU и проверка соответствия лимитов ресурсам VM по умолчанию отключены. Чтобы выполнить их при следующем деплое, задайте `yarn_check_resources: true` в `edge/group_vars/all.yml`. Проверка согласованности самих лимитов выполняется всегда, без обращения к VM.

Для каталогов истории устанавливаются владелец `hdfs:hadoop` и права `/mr-history` — `755`, `tmp` — `1777`, `done` — `750`.

## Веб-интерфейсы

На локальном устройстве из `hw2/infra` запустите:

```bash
./web-ui.sh
```

Скрипт возьмёт адреса из inventory ДЗ1 и откроет туннели из [шага 10 ручной инструкции](../manual-installation.md#шаг-10-открыть-веб-интерфейсы-через-ssh-туннель). Пока открыто SSH-соединение, доступны:

| Интерфейс | URL |
| --- | --- |
| ResourceManager | `http://localhost:8088` |
| JobHistoryServer | `http://localhost:19888` |
| NodeManager nn | `http://localhost:18042` |
| NodeManager dn0 | `http://localhost:18043` |
| NodeManager dn1 | `http://localhost:18044` |

Локальные порты должны быть свободны. Туннели слушают только `127.0.0.1`. Остановка — `Ctrl+C`. Прямые ссылки внутри Hadoop UI могут содержать внутренние адреса кластера; отдельные интерфейсы открывайте через локальные URL из таблицы.

Это доступ через SSH, а не постоянная публикация веб-интерфейсов в интернете. Публичный reverse proxy остаётся отдельной частью задания; данный деплой повторяет способ доступа из текущего гайда.

## Повторная проверка без настройки и перезапуска

На edge из каталога `hw2/infra/edge`:

```bash
ANSIBLE_CONFIG="$PWD/ansible.cfg" ansible-playbook check.yml
```

Команда проверит сервисы и выполнит новую WordCount-задачу. Если она завершилась с ошибкой, смотрите вывод Ansible и логи демонов в `/opt/hadoop-3.4.0/logs`.
